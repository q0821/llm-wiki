「每個人都應該學會利用 AI 與自動化工具，打造專屬的 Skill 或 Agent，以持續提升與實現自己的生產力」
​
如果要用一句話來概括今年 AI 的走向，我會選這一句
​
我們常常習慣比較或討論哪家模型最聰明？但我覺得現在真正重要的事情，已經慢慢變成：「你有沒有替自己建構一套 Agent 體系？」
​
.
.
​
## 從會用介面到擁有團隊
​
回顧以往，大多數人使用 AI 的方式，大略停留在高級搜尋的階段，但本質上依然是一問一答的來回，對他們來說，他們是在跟一個很聰明的機器人聊天，還談不上是能接手自己任務的系統
​
所以近期大廠做的事情，都在往同個方向靠攏，
​
例如 OpenAI 的 Ultra Mode，可以同時調度多個 Agent，並行跑不同子任務；
而 Anthropic 的管理者框架，則是把最強的 Fable 5 變成管理者，把大量執行工作交給更便宜的 Sonnet 子 Agent；
又或者是 Cursor 的 Sand 智能體，他在嘗試做一個桌面級的代理人，跳出 IDE 的去指揮各種 coding agent、工具和工作流
​
參考以上的策略會發現，他們在做的事情都是讓模型從回答問題，升級成協調多個子任務的協作者
​
如果我們把這件事收斂到個人層面，也可以用一句話概括：「每個人都可以擁有一隻由自己定義的 AI 團隊」，而這支團隊就是我們自己建構的 Skill 和 Agent
​
.
​
## 為什麼要自己建立？
​
「我用現成的 ChatGPT、Claude 不就好了？為什麼還要自己建立 Skill 或 Agent？」
​
我覺得至少有三層原因：
​
### 1. 現成的 Agent 還無法完全懂我們的語境
​
再強、再通用的 Agent，他也無法在第一時間參透以下內容：
​
- 專案裡的專用名詞
- 團隊的程式碼架構
- 我們自己的寫作、設計風格
- 我對於「夠好」和「不行」的差別在哪裡
​
這些東西，御三家做不出來，也不該由它們來做，應該透過我們自己建構的 Skill、Agent，然後長期的投餵，持續做這兩件事情：
​
a. 把自己反覆使用的判斷、套路、標準，抽象成一個可重用的步驟
b. 把這些步驟交給 AI 反覆執行，在每一次執行裡繼續打磨
​
久而久之，它會越來越像一個我們親手訓練出來的資深特助
​
### 2. 真正節省的不是打字時間，而是判斷的時間
​
我忘了在哪一篇文章看過的，而至今依然令我印象深刻的一句話：「自動化的真正價值，不是減少點擊，而是減少『重複判斷』」
​
想想我們每天最消耗能量(可能只有我)的部分，其實不是打了多少字，而是重複的溝通，例如：
​
- 重複想同一類的問題
- 每次都重新跟 AI 解釋同一套背景
- 反覆手動檢查那些你早就知道該怎麼驗收的細節
​
而當我們把這些都寫到一個 Skill / Agent 裡時，我們往後的輸入，只需要給最少的必要資訊，而中間的過程 (包括拆解、調用工具、並行處理) 都會由 Agent 自己完成。
​
Agent 輸出資訊時，也會自動帶入我們定義好的驗收標準、格式以及下一步動作
​
我們省下的除了那幾分鐘的操作外，還多了滑手機的時間(X
​
### 3. 當模型差距愈來愈小時，誰更會設計 Agent 將會放大差距
​
GPT‑5.6、Fable 5、Grok 4.5 …… ​ 
​
不知道大家有沒有這種感覺，頂級模型的聰明程度，其實愈來愈接近了
​
如果你不是專業的評測人士，其實在很多任務上，我們不會再被模型能力給限制，完成專案的差別更多是在於以下幾點：
​
- 利用上下文
- 對的 Skill
- 把任務拆解到合適的範圍(粒度)
- 設計穩定可重用的迴圈
​
也就是說，讓大廠去卷模型、卷聰明；我們能做的，是卷協作，這依然是體現在如何設計 Skill 和 Agent 上
​
.
​
## 什麼叫為自己建一套 Skill / Agent？
​
說真的，這不是什麼高大上的東西，所以不用想得太複雜，也不要覺得第一次就要做到 100% 完美，只要有一個共識：這是一個會不斷持續迭代的文件，你需要的是耐心和動手做的決心
​
如果你願意，我們可以從以下三個面向進行發想：
​
### 1. Skill：把你已經會的事情，寫成可以被 AI 重複執行的說明書
​
- 幫我把一篇技術文章，轉成適合 FB 長文 + 三張圖的結構
- 根據我專案裡的約定，幫我寫一份 PR 描述，包括：動機、變更點、風險、回滾方式
- 把逐字稿、原始的會議記錄變成我習慣的會議摘要格式：背景 → 結論 → 行動項
​
這些一開始通常是提示詞，但當你發現你開始想要或開始做以下規劃時，他就已經趨向於一份 Skill 了：
​
- 有固定輸入跟輸出的格式
- 約束風格和邊界
- 開始加上簡單的檢查規則，例如要包含某些欄位... 等
​
### 2. Agent：讓 Skill 自己串起來
​
有了 Skill 之後，下一步要思考的是誰負責編排？如何根據情境選擇對應的 Skill？如果中途失敗，怎麼知道要重試、換條路，或是回滾？
​
這時候就需要一個上層的 Agent，他可以理解我們的目標，並將目標拆成數個子任務，給子任務挑選合適的 Skill 或工具，並控制執行的順序以及是否要並行？
​
最後把結果收集回來，做一次完整的檢查與總結
​
熟悉這個操作嗎？這就是文章一開始提到的 Ultra Mode、管理者框架、Sand，他們在更底層會做的事情
​
而我們要建構的就是這一套模式，差別在於我們希望他只會替我們一人打工
​
### 3. 系統：讓這些東西可以長期累積與迭代
​
最後的重點，不是寫出來就沒事了，而是要持續的迭代與維護
​
我們可以這樣做：
​
- 把 Skill 與 Agent 配置放在 Git Repo，並詳細說明這套工作流程
- 透過筆記或文件資料夾，記錄每次改動背後的原因
- 生成一套最小可用的發佈流程，例如改了提示詞後在專案上試跑，通過就 commit and push
​
建構一個系統是為了未來的自己，我們現在把 Skill、Agent 做好，紀錄寫清楚，未來就能少踩坑、少浪費 token，少 debug
​
.
​
## 如果想從小事做起，可以從哪裡開始？
​
思考一下自己每週至少要做三次的小任務，把它寫成一個固定的 Skill 或 Agent，而不是一段提示詞
​
可參考的情境如下：
​
- 每週一篇部落格、一封電子報的結構化大綱
- 每次 PR 的 changelog、breaking changes 的提醒
- 每天的工作回顧，以及隔天最重要的三件事
​
關鍵在於，要寫成 AI 也能看得懂的步驟，不要只給一個模糊的指令；再來就是在一個固定的地方把 SKill 給固定起來，而不是散落在不同的聊天記錄中
​
也許你會覺得我要推薦你放在 Hyday 筆記軟體，但不，一切關於 Skill、Agent 的維護，我個人推薦的依然是 GitHub
​
當我們有了第一個真正意義上是自己做、自己維護的 Skill 後，就會開始反過來想，哪些東西可以交給 Agent 處理？哪些原本由人類做的判斷，可以拉出 90% 交給自動化來處理？
​
這一刻開始，我們與 AI 的關係，不再是使用一個聊天機器人，而是走向擁有一套為自己工作的 AI 體系
​
我們要做的，就是讓這套體系日復一日的把我們的生產效率，提升到一個別人難以企及的高度上 (俗稱壓榨 (X
​
而這套體系，只有你自己能為自己建造出來
