### 1. Hi Day 筆記軟體：以 AI 協同開發的實戰經驗

#### 講師背景與開發動機

- MUKI 老師為具設計背景的前端工程師，曾出版程式與時間管理書籍，自 2008 年起經營個人部落格（muki.tw）
- 曾使用 Evernote、OneNote、Notion、Obsidian 等工具，遭遇兩大痛點：
  - **痛點一**：Obsidian 自由度高，超過 3/4 注意力花在設定外掛與調整佈景，非寫筆記本身
  - **痛點二**：不花大量精力維護分類系統（卡片盒、PARA、MOC），筆記難以串連與檢索

#### Hi Day 軟體介紹

- 開發時間：2026 年 1 月開始，五個月後於 5 月中旬推出正式版
- **儀表板（Dashboard）**：首頁快速收斂資訊，含任務、日記與 AI 生成的「洞察」，提示未完成事項並給予建議
- **整合行事曆**：串接 Google 行事曆，呈現每日時間安排與寫作紀錄
- **AI 代理人（Agent）**：透過 Clocko、Codeless 等 API 供應商，讓使用者以對話方式與 AI 互動（**STT 待校：Clocko / Codeless 可能是 Claude / Codex**）
- **Life Log 功能**：記錄整天工作流程，含五個指標：`開始`、`結束`、`當前`、`想法`、`重要`
- **AI 標籤分析**：
  - **總覽**：收集標籤 90 天內紀錄，整理演變脈絡、反思提問與建議
  - **時間軸**：顯示標籤在每天出現的位置，快速查找
  - **90 天重點摘要**：分為「已觀測」、「關鍵決策」、「待處理事項」，可直接建立任務
- **Clocko Channel 整合**（**STT 待校**）：常駐側邊欄，AI 可存取整台電腦資料，執行上網、整理筆記、爬取資料等任務

### 2. AI 導向的系統架構師角色與 CICD 全流程

#### 角色定位與三大核心

- 從單純寫程式的工程師，轉型為能帶領 AI 團隊的系統架構師
- **定義**：明確化模糊需求，制定「何為好、何為高品質」，定義可上線準則與設計系統規格（UI 元件、顏色、設計細節）
- **決定**：判斷 AI 生成的程式碼是否通過、是否允許 AI 部署上線，決定 AI 介入的範圍與時機
- **負責**：系統出事時由真人承擔，親自審閱 AI 所寫內容，必要時立即終止並由人類接管

#### CICD 全流程與 AI 協作

- 從規劃、設計、開發、上線、QA、更版到維運，皆可與 AI 協作
- 重點在於人類層面制定標準、監督與把關，而非與 AI 搶工作

#### 設計系統與 Design Token

- 人類轉為設計系統守門人，定義 UI 元件規格、顏色規則，轉化為 AI 可理解的 design token
- 在自然語言提示中引用 design token，確保前端輸出一致性

#### 權限控管與資料安全

- 不給予 AI 過高權限，設置安全邊界，避免批次刪除等高風險操作
- 需具備基本資料安全常識，配置防護機制與審核流程

#### 工具與技能實務

- **規劃階段：Superpowers**（**STT 待校：super product → Superpowers**）
  - 功能：腦力激盪、計劃拆解、子代理開發（寫程式與測試）
  - 注意：因階段拆分細，「燒 token」較多；Pro 方案需斟酌使用

- **設計階段：Front End Design**（**STT 待校：Cloud Code 官方技能 → Claude Code 官方 skill `frontend-design`**）
  - 用自然語言指示，引用既有 design token，生成 A/B/C 三個 HTML 版本供挑選
  - 可混搭版本（如 A 的框線 + B 的選單 + C 的字型），AI 自動融合生成新版本
  - 實務案例：為「書架」新功能製作篩選介面，並補齊 loading 畫面

- **開發、建置、測試與釋出**：常用 git 技術、deep link 與多種 AI 技能，完善 CICD 整合流程

### 3. AI 輔助開發工具介紹與風險管理

#### 主要工具介紹

- **Deep Wiki**
  - 將任何 GitHub 公開專案轉換成可互動的文件，讓使用者直接對專案提問
  - 官方網站：`deepwiki.com`；不知名專案可手動加入掃描
  - 以詢問 Vue 生命週期為例，AI 從專案撈取資料並彙整成易懂內容

- **Deep Wiki NCP**（**疑似 MCP 而非 NCP**——transcript 多次說「NCP」可能是 Plaud STT 對「MCP」的口音轉錯）
  - 安裝於終端機中，無需離開開發環境即可呼叫 Deep Wiki 查詢
  - 透過自然語言指令 `使用 Deep Wiki NCP 幫我搜尋...` 呼叫，直接搜尋 GitHub 倉庫原始資料，準確率高（約 99%）

- **GitHub CLI（gh）**
  - GitHub 官方命令列工具，在終端機完成 push、pull、查看 CI/CD 狀態、審查 PR 等操作
  - 可結合 AI 以自然語言操作，省去記憶 git 指令的麻煩

- **Git Work Tree**
  - 為一個 repo 建立多個獨立工作目錄，同時進行多項任務而不互相干擾
  - 已成為 AI 開發的常用模式（如 Claude 的 web app 會自動建立）（**STT: Cloud → Claude**）

- **AI 模擬瀏覽器操作**（**STT: Cloud 擴充功能 → Claude 擴充功能（Claude in Chrome）**）
  - 類似 Computer Use 功能，讓 AI 模擬真人在 Chrome 進行點擊、開啟網頁、讀取資料
  - 透過 Claude 擴充功能使用，可開啟開發者工具（console）進行除錯，實現整套自動化流程

#### AI 開發風險與邊界設定

- AI 產生程式碼速度極快，人類難以同速審查，持續接受而不審查會快速累積技術債
- **邊界設定技巧**：
  - **`CLAUDE.md` 檔案**（**STT: cloud.md → CLAUDE.md**）：Claude AI 會優先讀取，可用強烈措辭列出不得修改的項目
  - **`settings.json`**：定義 AI 允許或禁止使用的指令，可與 AI 討論後產生
  - **優先使用工具而非模型自律**：工具通常不出錯，AI 長時間對話後可能「忘記」指令
  - **保護重要檔案**：如 `.env` 等環境設定檔，明確禁止 AI 讀取或修改
- **提交前流程（Pre-commit）**：
  - 禁止 AI 直接合併到主分支（main/master）
  - 合併權保留在人類手中
  - 使用 Hook 建立 commit 前自動化防線（如檢查 TDD、Code Review 完成情況）

#### 測試驅動開發（TDD）

- TDD 三步驟：
  - **開紅燈**：先寫一個會失敗的測試案例
  - **開綠燈**：用最小可行程式碼讓測試通過
  - **重構**：優化程式碼，使其更具防禦性與邊界性
- 可利用 AI Skill（如 Super Powers 內建 TDD Skill）在開發過程中自動執行

#### 導入 AI 至既有專案

- 最大挑戰是 AI「不懂裝懂」而幫倒忙
- **`Understand Anything` Skill**：將專案所有檔案整理成互動式知識圖譜，幫助 AI 掌握專案全貌

### 4. 建立專案共同語言：Understand Anything 與 Agree with Docs

#### 工具定位與使用偏好

- **Understand Anything Dashboard**：產生知識圖譜與領域（Domain）說明
  - 結構視圖（偏程式細節）因 UI 字小、閱讀吃力，通常略過
  - **領域視圖**為主，用以理解業務邏輯與專案脈絡
- **Agree with Docs**：工程師與 AI 對話的流程工具箱，主要用於建立詞彙表與產生 context 文件（nd 檔案）

#### 工作流程串連

1. 用 Understand Anything Dashboard 產生「知識圖譜」
2. 用 Agree with Docs 建立「詞彙表」與 context 文件
3. 回到 Understand Anything 的「Understand Domain」skill，指示 AI 讀取詞彙表，產生「商業流程/商業邏輯」文件

#### 詞彙表（Glossary）設計

- 工具掃描專案特殊功能與命名，詢問講者確認後產出定義
- 準確度：詞彙表約九成，業務邏輯約七至八成
- 範例名詞：`tag`、`entity`、`backlink`（均於 highlight 功能中定義）
- 使工程師與 AI 在專有名詞層面對齊，避免語義偏差與誤解

#### 可交接性與應用場景

- 輸出可作為 AI 學習材料，亦可作為新人交接文件，快速建立對專案流程的全貌理解

#### 面對 AI 失控時的干預策略

- 常見失控現象：突然轉為韓文，或出現大量中英混雜術語
- 干預方法：
  - 隨時按「跳出鍵」中斷當前輸出，重整對話方向
  - 直接重申當前目標，要求 AI「用白話文」說明，降低術語密度

### 5. AI 時代的角色轉變、回溯機制與長足型思考

#### 與 AI 協作的控制與治理

- 為每個任務事先定義範圍、門檻與預算，要求 AI 先產出計劃與驗收方式，人類負責稽核或拒絕
- **Effort 等級控制**：依任務難度設定 High、XHigh、Low 等級，調節 AI 的投入範圍

#### Claude 中的回溯與防線機制（**STT: Cloud → Claude**）

- **Checkpoint 與自動回溯**：於生命週期節點建立還原點，分手動指定與 Claude 自動建立兩類
- **人工中斷與回退**：雙擊跳出呼叫回退選單，基於過往對話與檔案更動進行選擇性捨棄
- 建議遇到失控時不要猶豫，隨時中斷並回到安全狀態再重新開發

#### 人類角色轉變與長足型思考

- 工程師不被取代，而是工作內容改變：從「寫程式」轉為「規格設計、邊界設定、風險承擔與決策」
- 人類的靈感與沉澱需要時間與環境切換，AI 無法取代此過程
- 透過 brainstorming 與 plan 階段強制讓 AI 與人共同釐清需求，再開始執行，避免被 AI 速度牽引

#### 與 AI 和平共處的實務準則

- **甜蜜點**：人定方向與規格，AI 協助執行；既不被 AI 牽著走，也不過度堅持己見
- **人定義「做對的事」**：AI 能把事情做完，但只有人能判斷何謂「對的事」
