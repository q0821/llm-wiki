# AI 協作真正省的是「決策次數」（酒Ann，2026-06）

一篇個人實戰分享文：作者「酒Ann」用 **ChatGPT（產品型 AI）+ Claude Code（工程型 AI）** 雙軌協作，5 天約 20 小時（≈3 個工作天）獨力完成一套公司內部 CRM / AI 內容工作台系統（自述 12 功能分區、202 功能模塊、53 個 cron）。文章重點不在「做了多少功能」，而在**萃取出的一套協作方法論**，並附完整 15 條 ChatGPT 專案協作 Instructions。

## 一句話定位

AI 協作真正省下的不是寫程式時間，而是**決策次數**——把大量小決策從「當下大腦即時判斷」轉移到「事前設計好的流程與規則」，人只在高風險節點拍板。

## 核心論點拆解

### 1. 決策次數是隱形成本（全文骨幹）

- AI 協作省下的是三件事：① 重工成本 ② 上下文理解成本 ③ **決策腦力**（最關鍵）。
- 一天 5 小時的 AI 協作，作者估算要做 **80–120 次小決策**：要不要修？要不要 commit？要不要 push？要不要改 schema？要不要開新 task / 換 session？
- 「你的腦不是被一個大決策耗乾的，而是被很多小決策慢慢消耗掉。」
- AI 很常把判斷丟回給人 → 若每步都要人重新判斷，等於把「寫程式的疲勞」換成「決策的疲勞」，不一定省腦力。
- → 對應新概念頁 [[決策疲勞]]（衡量 AI 協作效率的人因框架）。

### 2. 把操作分三層：自動 / 回報 / 確認

| 層級 | 性質 | 範例 | AI 行為 |
|------|------|------|---------|
| ① 可自動執行 | 低風險、唯讀 | 讀檔、grep、看 branch/log、跑型別檢查、build | 直接做，做完回報 |
| ② 先做但要回報 | 中風險、不改系統 | 技術分析、檔案修改計畫、列風險、設計資料流、UI flow | 先產方案，人再判斷 |
| ③ 必須先確認 | 高風險、重工成本高 | 改 schema / migration、push main、deploy、改正式環境、刪資料、批次改會員、改權限 | 停下來問 |

- 核心不是「讓 AI 全自動」，而是**讓 AI 知道什麼不用問、什麼一定要問**。
- 機制本質：把「即時決策」轉成「預先規則」——即時決策耗腦，預先規則省腦。
- → 這正是 Anthropic / Claude Code permission mode（allow/ask/deny）的個人語意版；亦呼應 [[Harness-Engineering]] 的安全邊界設計。

### 3. 任務設計 > prompt 技巧（Non-scope 是精髓）

- 「AI 協作最重要的不是 prompt 技巧，而是任務設計能力。你不能只是跟 AI 許願，而是要設計一段又一段的工作流程。」
- 一份好任務指令至少含六件事：**① 背景 ② 已確認的產品決策 ③ 本次 Scope ④ Non-scope ⑤ 安全限制 ⑥ 輸出格式**。
- **反直覺重點**：作者反覆強調主動寫 **Non-scope（這次明確不做什麼）**——「不改 schema / 不做 migration / 不 push main / 不 deploy / 不覆蓋原資料 / 不擴大到 Phase 2」。指令寫得細不是為了控制 AI，而是**降低自己後續的決策負擔**（規則寫好了，這輪就不能動工，不用每次重想「這步可不可以」）。
- → 呼應 [[CLAUDE-md]] / [[AGENTS-md]] 作為持久規則層；與 [[Prompt-Pack-Pattern]]（多段 prompt 串工作流）同源。

### 4. 流程才是真正的產出

- 「20 小時真正完成的不是功能，而是一套協作流程。」十步循環：
  Discovery → 收斂成產品決策 → 拆小 Task → AI 實作 → AI 驗證 → 人做驗收 → 部署後確認正式站 → 踩坑寫成 SOP → 想法放 Roadmap（不插隊）→ 換新 session 用乾淨交接摘要接續。
- **先 Discovery 再 Coding**：先讓 AI 研究根因（是 UI/資料/API/流程問題？要不要動 DB？影響權限嗎？），避免「以為要做 A、真正問題是 B」的重工。「AI 很快，但方向錯，快只會讓你更快走到錯的地方。」
- **小 Task 降低大腦切換成本**：大 task 塞太多決策；小 task 一輪只做一件（只查問題 / 只修 UI / 只驗部署 / 只寫計畫）。
- **每次踩坑變 SOP**：問題不只修掉，要問「為什麼發生？下次怎麼避免？要不要變固定檢查流程？」→ 直接對應 [[Ratchet-Pattern]]（每次錯誤編碼成永久規則）。
- **想法先進 Roadmap 不立刻做**：防 scope creep，「AI 時代真正困難的不是把東西做出來，而是知道什麼時候先不要。」

### 5. 換 session + 交接摘要（對抗 [[Context-Rot]]）

- **反直覺**：專案上下文要累積，但**不代表對話要無限延長**。
- 對話越長，AI 越容易混到舊資訊（已完成的任務、改掉的決策、過期錯誤訊息），結果「越來越蠢」。
- 作法：每完成一個重要階段就換新 session（ChatGPT 與 Claude Code 都換），換前讓 AI 產一份**交接摘要**（branch / 最新 commit / 已完成 / 待辦 / 本次不能碰 / 下一任務 / 產品決策）。
- 「把上下文從『聊天紀錄』整理成『專案狀態』」——聊天紀錄很長但不一定有用，專案狀態很短但每行都能幫 AI 決策。
- 換 session 也降低**人的**記憶負擔：把記憶交給文件、執行交給 AI、決策留給自己。

### 6. 把 AI 分角色（≠ 全交給同一個 AI）

- ChatGPT 當「產品型 AI」（看回報、做產品/架構判斷、整理交接摘要），Claude Code 當「工程型 AI」（進本機讀程式、改檔、跑測試、回報），人只搬運「決策需要的資訊」。
- → 這是 token 省很多的真正原因（少做無效上下文搬運），亦呼應 [[Subagent-Driven-Development]] 的角色分工精神（差別：此處是兩個獨立產品的人工編排，非單一 harness 內的 subagent）。

**錯位 A —「反直覺稀釋」（第 6 大類候選，全新）**

你把第二點記成「明確定義好**現在要做什麼**會比較快」。但文章反覆強調的反直覺核心其實是定義「**不做什麼（Non-scope）**」——整條 Instructions 第 5 條、正文第 425–442 段都在講 Non-scope，作者明說「我很重視『這次不做什麼』」。

### 重組路徑建議（針對你的真實場合「改自己的 Claude + 協作習慣」）

立刻可做的三件，全部寫進你自己的 `CLAUDE.md`：

1. **加一段「決策權限三層」到 CLAUDE.md**：明列「可直接做（唯讀/grep/build/型別檢查）/ 先做要回報（分析/計畫）/ 必須先問（schema/migration/push main/deploy/刪資料）」。這直接把你跟 Claude Code 的小決策次數砍下來。（你既有的 CLAUDE.md 其實已有 dev-principles / preflight 等規則，這層是補上「風險分級」的缺口。）
2. **每個任務先寫 Non-scope，不是先寫 Scope**：針對錯位 A 的矯正——下次開任務，**先列「這輪不做什麼」**再列要做什麼。把鋒利的那一半找回來。
3. **養成「換 session + 交接摘要」習慣**：長對話到一段落，讓 Claude 產一份「branch / commit / 已完成 / 待辦 / 本次不碰 / 下一步」的交接摘要，再開新 session 貼進去。對抗 [[Context-Rot]]，也降低你自己的記憶負擔。
