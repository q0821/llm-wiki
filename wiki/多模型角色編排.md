# 多模型角色編排（Multi-Model Role Orchestration）

**依「任務類型／角色」把工作分派到不同模型層級：貴的前沿模型只做規劃與 review，便宜模型做執行。** 目的是在保住品質的前提下大幅降低 token 成本。是 [[Harness-Engineering]] 在「成本」維度的具體實作。

## 核心 benchmark（Anthropic）

| 模式 | 配置 | 效能 | 成本 |
|---|---|---|---|
| 全前沿 | 全程 Fable 5 | 100%（基準）| 100% |
| **Advisor** | Sonnet 5 主 + Fable 5 顧問（只在關鍵決策介入）| 92% | **63%** |
| **Orchestrator** | Fable 5 規劃/拆解/指派 + Sonnet 5 執行 | **96%** | **46%** |

> 一句話：「Fable 5 orchestrator + Sonnet 5 workers achieves 96% of all-Fable performance for 46% cost.」

## 角色分類（[[src-nanako-pilotfish|pilotfish]] 的六角色）

關鍵在**「便宜模型只放在品質對模型層級不敏感的工作」**——機械、搜尋——**「判斷類一律留前沿」**：

| 角色 | 模型層級 | 工作 |
|---|---|---|
| scout / Explore | Haiku | 唯讀查找 |
| mech-executor | Sonnet | 機械式模式工作 |
| executor | Opus | 需判斷的實作 |
| **verifier** | Opus | **獨立 fresh-context 對抗式 review** |
| security-executor | Opus | 資安敏感任務 |

這正好回答「何時該這樣用」：**機械/搜尋下放、判斷/驗證/資安留前沿。**

## 兩種實作路線

| 路線 | 代表 | 形式 |
|---|---|---|
| **打包工具** | [[src-nanako-pilotfish\|pilotfish]] | 一鍵裝進 `~/.claude/`，三層（settings.json 模型別名 / 六個 agent 檔綁層級 / [[CLAUDE-md\|CLAUDE.md]] 用角色名寫政策）|
| **手動指令** | [[src-zhongyea-orchestrator-cost\|@zhong_yea]] | 自建 `/orchestrator` 指令 + CLAUDE.md 預設模式 |

兩者講的是**同一個 benchmark 數字**，一個是工具、一個是手動教學。

## 設計原則（可遷移到其他 harness）

- **政策只寫角色名、不寫模型名**：模型綁定集中在各 agent 檔一處，換模型只改一處 → 對應 [[Ratchet-Pattern]]（設計要能抗模型汰換）
- **fresh-context 驗證勝過自我批評**：verifier 用獨立 context → 呼應 [[Harness-Engineering]] 的「裁判獨立性」與 [[Adversarial-Code-Review]]
- **別名（`best`/fallback chain）追蹤最新推薦版**，撐過模型 deprecation 週期

## 與本知識庫的關聯

- [[Harness-Engineering]] — 本概念是其「成本／裁判獨立性」維度的落地；verifier = 獨立裁判
- [[Managed-Agents]] / [[Claude Code]] — 執行載體

## 信心評估

- **中**：benchmark 數字來自 Anthropic 官方 eval（兩來源一致引用），但**是其 eval set 的平均值**，不保證落在特定 codebase；實際降本效益需個別工作負載實測
- **待驗證**：verifier 的 Opus token 開銷是否吃掉便宜執行省下的成本，取決於便宜模型的錯誤率

## 我的觀點

### 2026-07-11 — 決策不是「要不要用」，是「哪些任務可下放」

> 本段依 ingest 個人吸收機制產生。quiz 對象為本概念（pilotfish + @zhong_yea 的共同主張）。

**使用者立場**（#stance:conditional-adopt）
- 價值：省 token、省錢
- 疑慮（三點，全部命中要害）：①品質是否一樣值得 ②會不會省了錢卻花更多時間來回 debug、反而沒差多少錢還浪費時間 ③**何時該這樣用**
- 意圖：「如果值得當然導入」——條件式採用

**LLM 觀察**
- **疑慮③正是這套設計在回答的問題**：角色分類（機械/搜尋→便宜、判斷/驗證/資安→前沿）就是「何時該用」的答案。使用者的顧慮與設計者的顧慮同源。
- **框架需修正（本次錯位）**：使用者 Q2 用「值得就導入」的**全域二選一**框架，但這套的本質是**逐任務類型路由**，不是全域開關。真正該問的不是「值不值得用」，而是「我的工作有多少比例夠機械、可下放」。命名為「**全域決策 vs 逐類路由的框架錯位**」。
- **debug thrash 的真實風險**：使用者疑慮②成立——risk 來自「判斷工作誤派便宜模型」+「verifier 的 Opus 開銷」。且 96% 是 Anthropic eval 平均，不保證落在使用者 codebase。**只有拿自己的活實測才知道淨省多少。**

**重組路徑建議**
- 決策順序改成：先分「我的任務哪些是機械/搜尋類」→ 只下放這些 → 判斷/驗證留前沿 → 拿一批真實任務量 debug thrash 與淨成本
- 最省事的實測場就是**這個 wiki 的 ingest 工作流本身**（機械類：抓取/改 index/補 log/git；判斷類：個人吸收觀察、矛盾標註）

**Spaced retrieval 約定**：~2026-07-25（14 天後）。回測問句：「你決定某個任務要不要下放給便宜模型時，用什麼判準？」期待答「看它是機械/搜尋類還是判斷類」，而非「看整體值不值得」。#stance:conditional-adopt
